# Technical Specification: Project PIU (Personal Image Uploader) - Final

## 1. System Overview

**PIU** is a lightweight, resilient, and extensible multi-directory file-watching system operating on a global event-bus model. A single, long-running native Go binary monitors decentralized physical inputs (directories) and pipes new files to a NodeJS backend via `stdout`. Node processes files globally, applies pattern-matching rules, and dispatches them to specified Discord destinations (bot channels or webhooks).

To prevent event loss and minimize overhead, the Go process is spawned **exactly once** at startup. Any runtime modifications to the inputs configuration (Add, Update, Delete) are synchronized dynamically from Node to Go using a text protocol over `stdin`.

### Tech Stack

* **Front-end:** Angular 17+ standalone components, TailwindCSS (UI in English).
* **Back-end:** NodeJS + TypeScript, Express, `better-sqlite3`, `pino` + `pino-roll`, `proper-lockfile`, `uuid`.
* **Database:** SQLite (Embedded, local storage).
* **File-Watching Component:** Go (Golang) compiled native binary using `github.com/fsnotify/fsnotify`.

## 3. Database Schema (Decoupled SQLite)

### Table: `inputs`

Manages the entry points of the system. The backend reads this table to tell the Go component what to watch.

| Column        | Type        | Constraints               | Description                                                                |
| ------------- | ----------- | ------------------------- | -------------------------------------------------------------------------- |
| `id`          | INTEGER     | PRIMARY KEY AUTOINCREMENT | Unique identifier                                                          |
| `name`        | TEXT        | NOT NULL                  | Friendly name for the UI (e.g., "Main Screenshots")                        |
| `type`        | TEXT        | NOT NULL                  | Type of input source. v1 only supports `"directory"`                       |
| `source_path` | TEXT        | NOT NULL                  | Full local OS path (e.g., `C:/Screenshots`)                                |
| `extensions`  | TEXT (JSON) | NOT NULL                  | Whitelist of accepted extensions, lowercase, no dot. Default `["png","jpg","jpeg","gif","webp"]` |
| `is_active`   | BOOLEAN     | DEFAULT true              | Enables/disables watching for this input                                   |

### Table: `outputs`

A global registry of routing rules and Discord endpoints. Any file captured from any input is evaluated against this table.

| Column               | Type        | Constraints               | Description                                                                 |
| -------------------- | ----------- | ------------------------- | --------------------------------------------------------------------------- |
| `id`                 | INTEGER     | PRIMARY KEY AUTOINCREMENT | Unique identifier                                                           |
| `name`               | TEXT        | NOT NULL                  | Friendly name for the UI (e.g., "Factory Games Channel")                    |
| `input_type`         | TEXT        | NOT NULL                  | Filters which input source type this rule applies to (v1: `"directory"`)    |
| `type`               | TEXT        | NOT NULL                  | Destination type: `"discord_bot"` or `"discord_webhook"`                    |
| `file_patterns`      | TEXT (JSON) | NOT NULL                  | Array of glob/substring patterns. Empty array `[]` only when `is_fallback = true` |
| `is_fallback`        | BOOLEAN     | DEFAULT false             | True if this row is a fallback **channel** (catalog entry, no patterns)     |
| `is_default_fallback`| BOOLEAN     | DEFAULT false             | True for the single default fallback channel per `input_type`               |
| `fallback_output_id` | INTEGER     | NULL, FK → `outputs(id)`  | On routing rules: optional link to a fallback channel for no-match routing  |
| `destination_config` | TEXT (JSON) | NOT NULL                  | Polymorphic credentials (see below)                                         |
| `is_active`          | BOOLEAN     | DEFAULT true              | Enables/disables this specific routing rule                                 |

**`destination_config` shape by `type`:**

```json
// type = "discord_bot"
{ "bot_token": "MTg0OTI0OD...", "channel_id": "11223344556677" }

// type = "discord_webhook"
{ "webhook_url": "https://discord.com/api/webhooks/.../..." }
```

**Constraints enforced by the backend (not by SQL):**

* Multiple rows per `input_type` may have `is_fallback = true` (fallback **channels**).
* Only **one** row per `input_type` may have `is_default_fallback = true` (among fallback channels).
* When `is_fallback = true`, `file_patterns` is ignored (empty array), `fallback_output_id` must be null.
* Routing rules (`is_fallback = false`) may set `fallback_output_id` to reference a fallback channel.
* `destination_config` JSON shape must match `type`.

## 4. Component Specifications

### 4.1. Go Monitor Bidirectional Synchronization (`go_monitor/main.go`)

**Core Library:** `github.com/fsnotify/fsnotify`.

**Lifecycle Management:**

1. At boot, Node launches a single instance of the Go binary. Node queries SQLite for all active inputs (`WHERE type = 'directory' AND is_active = true`) and writes `WATCH:<source_path>\n` lines to the Go `stdin` to hydrate the baseline state.
2. The Go binary maintains an internal thread-safe map (`sync.Map`) of `root_path → watch context` (per-root cancel function and the set of subdirectories currently registered with `fsnotify`).
3. A background Goroutine inside Go continuously reads `os.Stdin` via `bufio.Scanner` for dynamic stream commands sent by Node.

**Recursive watching (manual):** `fsnotify` is not recursive. When a `WATCH:<root>` command arrives, the Go process performs `filepath.Walk(root)` to register every existing subdirectory with `watcher.Add()`. When a `CREATE` event fires on a directory at runtime, Go automatically calls `watcher.Add()` on the new subdirectory (and walks it recursively in case multiple nested directories were copied in at once).

**File-stability detection:** Files captured during a `CREATE`/`WRITE` event may still be growing. After the first relevant event for a file path, Go polls `os.Stat(path)` every **200 ms** and only emits the path to `stdout` once the file size remains identical for **600 ms** (3 consecutive stable polls). This prevents partial uploads.

**Initial scan policy:** On `WATCH:<root>`, **pre-existing files inside the directory are ignored**. Only files created/modified after the watcher is attached are reported. This avoids duplicate processing across restarts (existing transactions are recovered separately by the Node recovery scan; see 4.2).

#### Stdin Command Protocol Matrix

Each command is a single line terminated by `\n`. Paths are absolute, OS-native (backslashes accepted on Windows). The Go process treats the command as raw bytes up to the newline — no shell escaping is required.

| Operation        | NodeJS Event Action                                  | Stdin Command Format                            | Go Internal Action                                                  |
| ---------------- | ---------------------------------------------------- | ----------------------------------------------- | ------------------------------------------------------------------- |
| Create Input     | User adds a new active directory path.               | `WATCH:<source_path>\n`                         | Walks tree, registers each dir with `fsnotify`, stores cancel ctx.  |
| Disable / Delete | User toggles `is_active` to false or removes row.    | `UNWATCH:<source_path>\n`                       | Removes all sub-watchers under root, cancels ctx, prunes map.       |
| Path Update      | User changes an existing input's physical path.      | `UNWATCH:<old_path>\n` then `WATCH:<new_path>\n` | Atomic swap: stop the old root, start the new root.                 |

**Output channel separation:**

* `stdout`: one line per stable file path detected (`fmt.Println(absPath)`). This is the only thing Node consumes from `stdout`.
* `stderr`: all diagnostic logs (errors, watcher add/remove, etc.). Node forwards `stderr` to its own logger.

### 4.2. NodeJS Core, Routing & State Machine (`backend/`)

When Go pipes a stable absolute path into Node's `stdout`, Node orchestrates a **transaction** that may produce multiple **deliveries** (one per matching output).

#### 4.2.1 Extension filter

Before any routing, Node checks the file extension (lowercased, no dot) against the originating input's `extensions` JSON array. Files outside the whitelist are silently ignored.

When a file is accepted, Node **copies** it into the transaction folder under `pending/` (the original stays in the monitored directory). Upload and retries use the copy in `storage/`.

#### 4.2.2 Routing algorithm (fan-out + fallback)

1. Query active routing rules for the relevant `input_type`:
   ```sql
   SELECT * FROM outputs
   WHERE input_type = ? AND is_active = true AND is_fallback = false;
   ```
2. For each row, parse `file_patterns` and test whether **any** pattern matches the **basename** (glob-style via `minimatch`, or substring when no `*` is present). Matching is **case-insensitive**.
3. Collect the set of `output_id`s that matched.
4. **Fan-out:** the file is dispatched to every matched output (the rule's own Discord destination, not its linked fallback).
5. If the matched set is empty, resolve a fallback destination:
   - If all active rules with `fallback_output_id` set agree on the same id → use that fallback channel.
   - Else use the row where `is_default_fallback = true AND is_fallback = true AND is_active = true`.
   - If no fallback can be resolved, the file is moved directly to DLQ with an explanatory error.

#### 4.2.3 Transaction folder layout

Each captured file becomes one transaction folder identified by a UUID v4 (`<txn_id>`). The folder name includes the date bucket (local time of discovery, format `YYYY-MM-DD`).

```text
storage/transactions/image_upload/{pending|error|dlq}/YYYY-MM-DD/<txn_id>/
├── image.<ext>                   # working copy for upload (source file is not removed)
├── transaction.json              # immutable transaction metadata
└── deliveries/
    ├── <output_id_1>.json        # mutable delivery state
    └── <output_id_2>.json        # ...
```

**`transaction.json`** (written once, never mutated):

```json
{
  "txn_id": "f0a1b2c3-d4e5-6789-abcd-ef0123456789",
  "original_name": "Satisfactory_screenshot_01.png",
  "original_path": "C:/Screenshots/Satisfactory_screenshot_01.png",
  "input_id": 3,
  "input_type": "directory",
  "discovered_at": "2026-05-24T13:05:42.123-03:00",
  "file_hash_sha256": "9f86d081884c7d659a2feaa0c55ad015a3bf4f1b2b0b822cd15d6c15b0f00a08",
  "extension": "png"
}
```

**`deliveries/<output_id>.json`** (mutated on every attempt):

```json
{
  "output_id": 7,
  "output_type": "discord_webhook",
  "status": "pending",
  "immediate_attempts": 0,
  "global_reprocesses": 0,
  "last_error": null,
  "last_attempt_at": null
}
```

`status` ∈ `pending` | `success` | `error` | `dlq`.

#### 4.2.4 Per-delivery state machine

For each delivery file in status `pending`, Node calls the adapter matching `output_type`:

* **`discord_bot`** → `POST https://discord.com/api/v10/channels/{channel_id}/messages` with `Authorization: Bot <bot_token>`, `multipart/form-data`, field `files[0]` carrying the image binary.
* **`discord_webhook`** → `POST <webhook_url>`, `multipart/form-data`, field `files[0]`. No Authorization header.

State transitions per delivery:

* **HTTP 2xx** → `status = "success"`, write `last_attempt_at`, clear `last_error`.
* **Failure (network error, HTTP 4xx/5xx except 429)** → increment `immediate_attempts`, record `last_error`.
  * If `immediate_attempts < 3` → retry immediately (no sleep beyond the natural latency of the call).
  * If `immediate_attempts == 3` → set `immediate_attempts = 0`, increment `global_reprocesses`, set `status = "error"`.
* **HTTP 429 (rate limit)** → respect `Retry-After` header; this attempt does not count against `immediate_attempts`.
* **`global_reprocesses > 3`** → set `status = "dlq"`.

#### 4.2.5 Circuit breaker (error state)

When a delivery transitions to `status = "error"`, the entire transaction folder is moved to `error/YYYY-MM-DD/<txn_id>/` (if not already there). A 1-minute `setTimeout` per delivery in `error` is scheduled. When it fires, the delivery's `status` is flipped back to `pending` and, if at least one delivery in the transaction is `pending`, the transaction folder is moved back to `pending/YYYY-MM-DD/<txn_id>/`.

#### 4.2.6 Transaction finalization

After every delivery write, Node evaluates the transaction:

* All deliveries have status `success` → move the folder to `storage/confirmed/YYYY-MM-DD/<txn_id>/`, **delete the image binary** (only `transaction.json` and `deliveries/*.json` remain), emit `transaction_completed`.
* All deliveries have a terminal status (`success` or `dlq`) and **at least one** is `dlq` → move the entire folder to `storage/transactions/image_upload/dlq/YYYY-MM-DD/<txn_id>/`. Emit `transaction_completed` event with `dlq=true`.
* Otherwise → leave in `pending/` or `error/` as appropriate.

#### 4.2.7 Manual DLQ actions

* **Retry Now** for a `<txn_id>` in DLQ: for every delivery with `status = "dlq"`, reset `immediate_attempts = 0`, `global_reprocesses = 0`, `last_error = null`, `status = "pending"`. Move the folder back to `pending/`. Deliveries already in `success` are not touched.
* **Delete** for a `<txn_id>` in DLQ: recursively remove the folder.

#### 4.2.8 Recovery on boot

Before accepting events from Go, Node:

1. Walks `pending/**/transaction.json` and re-schedules any delivery in `status = "pending"` immediately.
2. Walks `error/**/transaction.json` and re-schedules a 1-minute timer for each delivery in `status = "error"`.
3. Leaves `dlq/` untouched (only the UI can act on it).

This guarantees in-flight transactions in `pending/` and `error/` are not lost across restarts.

#### 4.2.9 Input backlog scan (startup catch-up)

After recovery, before the Go monitor starts, Node scans each **active input** directory recursively. For every file whose extension is allowed:

* If `original_path` already appears in any `transaction.json` under `pending/`, `error/`, `dlq/`, or `confirmed/` → **skip** (already known to PIU).
* Otherwise → process as if the Go monitor had just detected it (copy to `pending/`, route, upload).

This catches screenshots created while PIU was offline. The Go monitor still ignores pre-existing files at `WATCH` time to avoid duplicating files that the backlog scan is about to handle; new files after boot are detected live.

**Performance:** building the index only reads JSON metadata (fast). Cost is dominated by walking the input folder(s). A dedicated screenshots folder with tens of files is negligible; monitoring an entire Steam `userdata` tree can take seconds and is not recommended. At most **100 files** per boot are processed; additional files wait for the next restart or a new file event.

### 4.3. Front-end (Angular UI — English only)

The interface is clean, responsive (TailwindCSS), and strictly in English. Standalone components, lazy-loaded routes.

#### Views

**Dashboard (`/`):**

* System status indicator (Running / Stopped) driven by the SSE connection state plus a `/api/dashboard/stats` heartbeat.
* Numerical cards: Total Synced, Currently Pending, Retrying (`error/`), Attention Required (`dlq/`).
* Live ticker fed by SSE events (`file_received`, `delivery_success`, `delivery_error`, `delivery_dlq`, `transaction_completed`).

**Inputs Manager (`/inputs`):**

* Form to register a directory: Name, Local Path, Extensions (multi-tag input, default seeded), Active switch.
* Table listing all monitored paths with toggle for `is_active`. Saving commits to SQLite and triggers `WATCH`/`UNWATCH` on the Go process.

**Outputs Routing Rules (`/outputs`):**

* Dedicated panel for the single Global Fallback per `input_type`.
* Table of specific rules. Add/edit form with:
  * Name, `input_type` selector (only `"directory"` in v1).
  * **Destination type selector**: `discord_bot` or `discord_webhook`. Form fields are conditionally rendered:
    * `discord_bot` → inputs for `bot_token` (password) and `channel_id`.
    * `discord_webhook` → input for `webhook_url`.
  * `file_patterns` as a tag input (each tag is a substring; case-insensitive at runtime).
  * Active switch.

**Troubleshooting / DLQ (`/troubleshooting`):**

* Grid of transactions stuck in DLQ, with thumbnail, original name, deliveries breakdown (which outputs failed and last error).
* Actions per transaction: **[Retry Now]** and **[Delete]**.

## 5. Operational Defaults

These defaults apply to v1 and may be revisited in future versions:

* **Network bind:** Express listens on `127.0.0.1:3737` only (loopback). No authentication; the app is single-user and local.
* **Single-instance lock:** `proper-lockfile` on `backend/.piu.lock`. Second instance exits with an explicit error.
* **Date bucketing:** all `YYYY-MM-DD` folder names use the **local time zone** at the moment of discovery / state transition.
* **Logging:** `pino` with `pino-roll` writes JSON logs to `backend/logs/piu.log` with daily rotation and 14-day retention. Go `stderr` is forwarded to the same log stream.
* **Go binary distribution:** compiled at install time via `npm postinstall` (requires Go toolchain on the dev/runtime machine). Output goes to `backend/bin/piu-monitor[.exe]`.
* **CORS:** `http://localhost:4200` is the only allowed origin (Angular dev server). When the frontend is built and served by Express, CORS is disabled.
* **Process supervision:** if the Go child process exits, Node restarts it with exponential backoff (1s, 2s, 4s, capped at 30s) and re-hydrates all active inputs.

## 6. Out of Scope for v1 (Roadmap)

Items intentionally deferred:

* Encryption at rest for Discord tokens.
* Authentication / multi-user support.
* Multiple fallbacks per `input_type`.
* Priority ordering between rules (current fan-out treats all matches equally).
* Deduplication by file hash.
* Prometheus metrics / external dashboards.
* Non-Discord outputs (S3, local archive, FTP, etc.).
* Non-directory input types (clipboard, browser extension, etc.).
